# Fan Control Core

笔记本风扇的控制核心。**一个接口，四个动作，谁都能用。**

```
{"op":"describe"}                    这台机器有几个风扇、走哪条通道、能不能写、给不给任意占空比
{"op":"read"}                        现在转速多少、占空比多少、归谁管
{"op":"set","fan":0,"percent":60}    把这个风扇固定在 60%
{"op":"boost","fan":0}               全速
{"op":"auto","fan":0}                交还给固件自己管
```

每个风扇会报一个 `supportsDuty`。**有的通道只有"全速"和"自动"两档**，
那种通道上 `set` 会**明确拒绝**，而不是收到 60% 就给你 100% ——
给一个和请求不一样的值却说成功，是这类工具最容易骗人的地方。

**`describe` 不碰硬件。** 它回答的是"能做什么"，那些由通道和机型决定，开机后不变；
"现在多少"是 `read` 的事。分开是有代价原因的：EC 每读一个字节要十几次固件往返，
而调用方光是画一次界面就会问好几遍能力 —— 混在一起之后列一次可控对象要十几秒。

标准输入一行一条 JSON，标准输出一行一条 JSON。调用方不需要知道这台机器
是 ASUS 的 WMI、Dell 的 SMM、还是同方公版的 EC —— 那是这个核心的事。

## 选哪条通道：两级路由，不是一串判断

一台机器落在哪条通道上是**查表**查出来的，不是一路 if 试出来的：

1. **一级路由：按平台。** Windows 一张表，Linux 一张表。表里每一行只说两件事 ——
   这是哪一类通道（上面那张表的五类），命中之后用哪个后端。这一级不碰硬件。
2. **二级路由：按识别依据。** 同一类里可能有好几家，由各自的识别依据决定 ——
   厂商接口的 GUID 在不在、固件指纹认不认。**各家的识别依据互不重叠**，
   所以一台机器在一个类别里最多命中一条，同类别内谁先谁后不影响答案。

识别依据必须是能把这台机器和别家区分开的东西，**不能是"试着写一下看行不行"**。
加一条通道就是往对应平台的表里加一行，核心不动。

厂商接口一律**按 GUID 找**，不按 Windows 上的类名 —— GUID 是固件里写死的，
上游实现也都用它指认；类名只是本地别名，各机型和驱动版本都可能不一样。
方法同理，按 MOF 里的方法编号找。参数也按 WMI 记录的序号和声明类型填，不按名字。

## 为什么不按品牌分

按"品牌/主板"分类会得到一个永远补不完的驱动库。真正稳定的分类是**控制通道**：

| 通道 | Windows | Linux | 什么时候用 |
| --- | --- | --- | --- |
| hwmon | — | `/sys/class/hwmon` | Linux 第一优先。内核已经导出可写 PWM 就直接用 |
| WMI / ACPI | OEM WMI / ACPI | 厂商内核驱动 + sysfs | 现代 OEM 主路径，Windows 第一优先 |
| HID | HIDClass | hidraw | Razer 这类；协议天然跨平台 |
| Raw EC | PawnIO | 专用 kmod / ec_sys | **只做兜底**，必须匹配固件指纹 |
| SMM | 专用实现 | `dell-smm-hwmon` | Dell 特殊路径 |

要维护的资产是**协议/机型 profile 数据库**，不是品牌驱动。

平台策略（静音/均衡/性能）**不在这里** —— 那些同时改功耗、温度目标和声学策略，
和"把这个风扇设到 60%"不是一回事，混在一层只会让两边都说不清。

## 安全规则（不可协商）

1. **同一时刻只有一个后端拥有写权限。** 两个后端同时写风扇，结果是谁也不知道现在是谁说了算。
   跨进程也算：EC 一台机器只有一块，访问是"下发命令、再取回结果"两步，中间被别的进程
   插进来取回的就是别人的结果。所以 EC 通道上加了**机器级命名互斥**
   （`Global\Uniwill-AcpiWmi-EcChannel`），宿主程序自己直接读 EC 的部分要用同一个名字。
   实测：核心单独跑 16 次开关全对，宿主同时在读 EC 时约四成失败；加锁后 16/16。
2. **有固件接口就不写 Raw EC。** WMI/ACPI 能做的事不绕到 EC 去做。
3. **Raw EC 必须匹配固件指纹。** 认不出的机器默认只读 —— 往陌生 EC 寄存器里写是要烧硬件的。
4. **退出即恢复。** 程序退出、崩溃、服务停止，都把风扇交还固件的自动模式。
   一个把风扇停在 20% 然后退出的程序，会把机器烤了。
5. **一切写入有硬边界。** 占空比、转速目标、曲线点都夹在机型 profile 声明的范围里。
6. **许可证隔离。** 寄存器映射和协议是事实，可以重新实现；直接复制源码前逐项审查许可证。

**"未实测"是字面意思**：那几条通道的协议事实取自公开实现（见下面的数据来源），
代码按事实写，但作者手上只有一台同方公版的机器。所以它们的边界画得很死 ——
固件不报出合理的风扇个数/转速就整条通道判为不可用，任意占空比一律不声称支持。
在那些机器上跑出什么结果，欢迎开 issue 告诉我们。

### Uniwill 那条为什么只有两档

`0x0751` 的那一位在固件里叫"全速模式"，字面意思就是全速 —— 置位之后两个风扇
都拉满，写多少占空比它都不看（实测要 70% 得到的是 100%）。所以那一位只用来做
`boost`。

真正的任意占空比应该走**自定义风扇表**：固件为每个风扇留了 16 个温区
（`0x0F00`–`0x0F5F`），把 0 区填成"0 到 115 度都跑这个速度"、其余 15 区填成
永远到不了的哑区，就等于一条水平线。参考实现就是这么做的，代码也写好了。

**但这台机器的固件不配合，实测踩到两个坑：**

1. `0x07C5`（分表使能）写不进去，固件拒绝。
2. 更糟的是它**只能置位不能清位** —— 试写之后 bit7 从 0 变成 1，之后怎么写都清不掉。

第二条是致命的：这条路会把机器推进一个**我们自己出不来的状态**。建表过程中副风扇
一度被留在 25% 占空比，比固件自己给的还低。一条走不回来的路不能留给用户走，
所以这条路在代码里关着，`supportsDuty` 如实报 `false`。建表代码留着 ——
换一台固件配合的机器、并且验证过能清位之后再打开。

（这也是为什么安全规则里要有"退出即恢复"和"认不出就只读"：
参考实现在它自己的机器上是对的，不等于在你的机器上也对。）

本机实测（MECHREVO / Uniwill，两个风扇）：
读到 2685 转 / 44.5%；`set 70%` 被如实拒绝；`boost` 之后两个风扇 4677 转 / 100%；
`auto` 之后回落到 2616 转 / 43.5%。

覆盖面靠的是 profile 数据库长起来，不是核心变复杂。

## 构建

```
dotnet build src/FanControlCore/FanControlCore.csproj -c Release
```

Windows 上的 Raw EC 通道需要管理员权限。
